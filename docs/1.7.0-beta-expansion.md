# WorldBinder 1.7.0: Projekte, Netzwerke und Replays / Projects, networks and replays

Die Erweiterungen verwenden die vorhandene Aufnahme, Recovery und Exportprüfung. WorldBinder speichert weiterhin ausschließlich Daten, die der Client empfangen hat. Die [Prüfmatrix](1.7.0-validation.md) trennt Datenprüfungen, echte Minecraft-Durchläufe und bekannte Grenzen.

## Deutsch

### Aufnahmeprofil und Container

Unter **Werkzeuge → Aufnahmeprofil** lassen sich Live-Entity-Filter, manuelles Container-Zusammenführen und dimensionsübergreifende Aufnahmen einstellen. Vor einer Aufnahme wird das Standardprofil bearbeitet; während einer Aufnahme gehört die Auswahl zum aktuellen Projekt. Optional kann sie zusätzlich als globaler Standard oder für die aktuelle Serveradresse gespeichert werden. Exportfilter bleiben davon unabhängig.

Live-Filter können herumliegende Items, XP-Orbs, Rüstungsständer, feindliche Mobs und einzelne Registry-IDs ausschließen. Die Prüfung erfolgt vor dem Erstellen eines WorldBinder-Entity-Eintrags. Minecraft verarbeitet seine Netzwerkpakete unverändert. Bereits vorhandene Projektelemente werden dadurch nicht gelöscht. Unpassende IDs werden vor dem Übernehmen abgelehnt.

Während einer Aufnahme erscheint bei unterstützten geöffneten Containern ein WorldBinder-Menü. Im optionalen manuellen Modus wartet die Übernahme auf deine Entscheidung; sonst gilt zunächst die gewählte Projektstrategie:

- **Behalten:** Der bisherige Projektstand bleibt bestehen.
- **Überschreiben:** Nur tatsächlich bestätigte aktuelle Slots ersetzen frühere Informationen.
- **Fehlendes ergänzen:** Nur unbekannte Slots ergänzen; bekannte Items und geprüft leere Slots bleiben erhalten.

Der Dialog zeigt empfangene und gesamte Slotanzahl. Unbekannt ist etwas anderes als leer. Die Entscheidungen lassen sich anhand des ursprünglichen Standes vor dem Öffnen erneut treffen; eine vorübergehende Auswahl überschreibt diese Ausgangsbasis nicht. Optional wird die Strategie zum Projektstandard. Das Menü verschiebt keine Items und sendet keine Inventarklicks. Der automatische Scanner bleibt verfügbar und wertet erst eine vollständige Antwort als erfolgreich. Für unbeaufsichtigtes Scannen den automatischen Modus mit Projektstrategie verwenden: Manuelle Bedienung unterbricht den Scanner, und eine ausstehende manuelle Entscheidung kann seinen Timeout erreichen. In Replay-Wiedergaben sind automatische Containerinteraktionen deaktiviert.

### Mehrere Dimensionen und Servernetzwerke

Neue Projekte können zusammengehörige Dimensionen gemeinsam verwalten. Alte Archive bis Format 3 behalten zunächst ihre bisherige einzelne Dimension; die neue Funktion kann bewusst eingeschaltet werden. Format 4 bleibt zu diesen Archiven und alten Recovery-Pfaden lesekompatibel. Ein früheres WorldBinder kann neue Format-4-Projekte nicht zuverlässig bearbeiten.

Ein Projekt hat eine dauerhafte Projekt-ID, eine Welt-/Netzwerkkennung und eine getrennte Backend-ID. Dimensionen besitzen eigene Chunks, Container, Entities, Kartenstände und Kartengeometrie. Der neueste eigene Spieler-/Enderchest-Stand wird beim Zurückwechseln nicht durch einen älteren Dimensionsstand ersetzt. F10 bietet eine Dimensionsauswahl für 2D und 3D; aktuelle Spieler und Erkundungsdaten werden nicht in einer fremden gespeicherten Dimension eingeblendet.

Im Singleplayer kann ein Dimensionswechsel automatisch innerhalb des Projekts fortgesetzt werden. Im Multiplayer kann derselbe Dimensionsname auch eine völlig andere Backend-Welt bedeuten. Bei unklaren Respawns, Reconfiguration und Transfers wird deshalb zuerst ein vollständiger Recovery-Stand geschrieben und die Datenaufnahme gesperrt. Im Zuordnungsdialog einen vorhandenen Backend-Eintrag wählen oder eine neue, getrennte Welt anlegen. Schließen des Dialogs lässt die Aufnahme sicher warten. Eine fehlgeschlagene Zwischenspeicherung zeigt den Fehler und einen Wiederholungsweg; sie erlaubt keine vorschnelle Zuordnung.

Bei deaktivierter Mehrdimensionsaufnahme bleibt das ursprüngliche Projekt beim Dimensionswechsel pausiert. Nach der Rückkehr zur ursprünglichen Dimension kann es bewusst fortgesetzt werden; die neue Clientwelt löst keine wiederholten Handoff-Sicherungen aus. Auch das Abbrechen einer Exportvorschau bleibt danach eine Pause ohne erneuten Exportstart.

**Dimensionswechsel diesem Backend zuordnen** ist eine ausdrückliche Vertrauenseinstellung für diesen Endpunkt. Nur aktivieren, wenn Respawn-basierte Wechsel dort tatsächlich zusammengehörige Dimensionen darstellen. Reconfiguration und native Transfers verlangen weiterhin eine Entscheidung. Server-Brand, Seed, gleiche Koordinaten oder `minecraft:overworld` werden nicht als Beweis für dieselbe Backend-Welt verwendet. Unter **Netzwerkprojekte** sind Server, Backend-Projekte und ihre Dimensionen erreichbar.

Ein Backend wird als eine Vanilla-Welt exportiert; seine Overworld, sein Nether und sein End landen in den zur Zielversion passenden Verzeichnissen. Andere Backends bleiben getrennte Projekte/Exporte. Custom Dimensions benötigen eine übertragbare empfangene Dimensionsdefinition oder einen bekannten Vanilla-Typ und eine passende Zielversion. Unbekannte Mod-Registrierungen werden nicht erfunden. Unterschiedliche empfangene Bilder mit gleicher Karten-ID erhalten in der Exportkopie eindeutige IDs samt angepassten Item-/Container-/Entity-Verweisen; das Archiv bleibt unverändert.

### Automatischer Start

**Capture automatisch beim Serverbeitritt starten** ist standardmäßig aus. Mit aktiviertem Schalter wartet WorldBinder auf eine geladene Verbindung und tatsächlich empfangene Chunks. Ein ausdrücklich für künftige Beitritte zugeordnetes Backend kann sein Projekt fortsetzen; ohne eindeutige Zuordnung entsteht ein neues, isoliertes Projekt. Ein manuelles Beenden startet nicht unmittelbar wieder eine Aufnahme. Serverprofile können das globale Verhalten überschreiben. Replay-Wiedergaben lösen diesen automatischen Start nicht aus.

### ReplayMod und Flashback

Die Integration ist optional und erfasst eine **laufende Wiedergabe**. Das gewünschte Replay mit dem passenden Original-Mod öffnen, dann über F9, F6 oder `/worldbinder` aufnehmen. Eine direkte Konvertierung von `.mcpr`/Flashback-Dateien ist nicht enthalten. Beide Original-Mods werden für Fabric angeboten; dies verspricht keine native NeoForge-Ausgabe dieser Fremdmods.

Die Kennung kommt aus der empfangenen Flashback-Aufzeichnungs-ID oder einem im Hintergrund berechneten ReplayMod-Dateihash. Unbekannte Adapter/API-Versionen sperren die Aufnahme verständlich, statt eine normale Serverwelt vorzutäuschen. Auch pausierte Wiedergaben erlauben die WorldBinder-Menüs und die begrenzte Verarbeitung bereits empfangener Daten; die Replay-Zeit wird nicht weitergeschaltet.

Zeitsprünge sperren die Eingangspipeline, bevor neue Pakete den alten Stand ändern können. Bei einem Rückwärtssprung bleibt der neuere Projektstand geschützt und pausiert. **Separates Projekt ab diesem Zeitpunkt** legt nach einer vollständigen Recovery ein neues Projekt aus dem tatsächlich empfangenen früheren Zustand an. Es kopiert keine späteren Chunks oder bestätigte spätere Luft in die Vergangenheit. Vorwärtssprünge und übersprungene Daten bleiben im Bericht als mögliche Lücken sichtbar. Das Schließen oder interne Neuverbinden einer Wiedergabe gilt nicht als normaler Server-Disconnect mit automatischem Export. Ein gespeichertes Replay-Projekt kann nach einem vollständigen Minecraft-Neustart mit derselben Aufzeichnung fortgesetzt und erneut exportiert werden.

Die Replay-Kamera ist kein eigener gesicherter Spielerstand. WorldBinder erfindet daraus kein Inventar, keine XP, Statistiken oder Fortschritte. Fehlende Containerantworten und Kartenbilder bleiben unbekannt. Die tatsächliche Kompatibilität pro Minecraft-/Replay-Version steht ausschließlich in der Prüfmatrix.

### Ältere Zielversionen

Für 1.13.2, 1.16.5 und 1.20.4 werden exakte Block-Registry-Fakten aus Mojangs generierten Serverberichten verwendet. Alte Ziel-IDs und Eigenschaftswerte werden gegen genau diese Version geprüft. Neu sind unter anderem historische Gras-/Schild-IDs, Wasserstand von Kesseln, strukturelle Schild-/Spawner-NBT-Konvertierungen und alte Biomnamen. Nicht verfügbare Schildrückseiten, Wachs und weitere Eigenschaften erscheinen als Verlusthinweise. Unbekannte Mod-NBT-Strukturen bleiben unangetastet.

1.13 benötigt den fertigen Chunkstatus `fullchunk`; ein modernes `full` kann insbesondere im Nether zur Neugenerierung führen. Der Exporter schreibt und der Prüfbericht kontrolliert jetzt den passenden Status. Das ist unabhängig von der Vollständigkeit einer Aufnahme: Eine gültige Datei kann weiterhin unbekannte Bereiche oder fehlende Inventar-/Kartendaten enthalten. Registry-Fakten und Provenienz sind unter `src/main/resources/data/worldbinder/target-registry/` dokumentiert und mit `node scripts/qa/generate-target-facts.mjs` aus den lokalen Berichten reproduzierbar.

## English

**Tools → Capture profile** configures live entity filters, manual container merging and multi-dimension capture. A profile belongs to the current project and can additionally become a global or per-server default. Live filters run before WorldBinder creates entity records; Minecraft still processes every required packet normally. Existing records remain intact. Export filters operate independently on the export copy.

The overlay in supported containers offers **Keep**, **Overwrite confirmed slots**, and **Fill missing slots** during capture. Optional manual-first mode waits for a decision; otherwise the project strategy applies automatically. Received empty slots are known; slots without a response remain unknown. Choices are recomputed from the baseline before that menu opened, and can optionally become the project default. No item movement or inventory-click packets are used. The scanner remains sequential and requires a full response. Use automatic mode and a project strategy for unattended scanning: manual input suspends the scanner, and a pending manual decision can reach its timeout. Replay capture does not perform container interactions.

Format-4 projects separate network/world identity, persistent project identity, backend identity and dimension scope. Older projects/recoveries remain readable and initially retain their previous single-dimension policy. Related dimensions share one exported world; unrelated backends remain separate projects. F10 can display each stored dimension without mixing current exploration or player markers into another scope. The latest received own player/ender-chest state survives a return to a previous dimension.

Unknown multiplayer world changes first commit Recovery and pause capture. Explicitly choose a known backend or create an isolated new world. Closing the assignment dialog keeps capture waiting safely; a failed handoff can be retried. The optional trust setting applies only to respawn-style dimension changes at that endpoint. Reconfiguration and native transfers still require a decision. Brand, seed, coordinates and dimension names never establish backend identity. The network-project browser groups saved backend projects and their dimensions.

With multi-dimension capture disabled, the original project stays paused when changing dimension. Returning to its original dimension permits deliberate resume without repeated handoff snapshots. Cancelling export review afterwards stays paused and does not restart export preparation.

**Automatically start capture on server join** defaults off. It waits for a loaded connection and actual received terrain. An explicitly assigned future-join backend can resume its saved project; otherwise a fresh isolated project is created. Per-server settings can override the global default, and a manual stop prevents immediate automatic restart. Replay playback never triggers auto capture.

ReplayMod/Flashback integration captures **during playback** using the normal pipeline, Recovery, map and export validation. It does not directly import replay files. Pause remains responsive without advancing the replay timeline. Seeks fence packet capture; rewinding protects the newer committed state and requires a fresh earlier-time project branch. Missing data in skipped intervals is reported. Internal replay reconnections/closure do not trigger ordinary disconnect export. Recording identity and the project survive a complete Minecraft restart. The spectator camera does not become invented own player inventory/statistics/advancements. Both upstream integrations are optional and currently Fabric tools; see the exact version/runtime matrix before assuming compatibility.

Exact Mojang registry facts for 1.13.2/1.16.5/1.20.4 improve old block/property validation and documented grass, sign, cauldron, biome and block-entity mappings. Unsupported sign data is reported, and unknown mod NBT is preserved. Minecraft 1.13 receives its actual final `fullchunk` status to prevent regenerated terrain overwriting the recording. Source archives and earlier revisions remain unchanged. Read-back validity and capture completeness remain separate results.
